# 需求文档：dingtalk-mcp（钉钉远程问答桥）

版本：v1.0（待评审）
日期：2026-10-18
关联文档：[设计文档](./design.md)

---

## 1. 背景

用 Qoder CLI（以及 Kimi 等其他 coding agent）干活时，经常跑到一个需要人做决策的点：选哪个方案、要不要执行某个不可逆操作、某个歧义按哪种理解处理。此时如果人不在电脑前，agent 就只能停下或自行猜测。

人在的地方是手机钉钉。本项目要做的是一座桥：**agent 把问题推到手机钉钉，人回复后 agent 继续工作**，并且这座桥可以随时一键关闭，退回纯本地交互。

## 2. 目标

| 编号 | 目标 | 说明 |
|---|---|---|
| G1 | 手机上能收到 agent 的问题并回复，agent 拿到回复后继续 | 核心价值，缺失则项目无意义 |
| G2 | 推送能力可开可关，关闭时完全不触碰钉钉 | 人在电脑前时不想被打扰，也不想多一层延迟 |
| G3 | 手机端与电脑端回复都作数 | 哪边先答哪边生效，另一边自动失效 |
| G4 | 同一套能力可被 Qoder 之外的 agent 使用 | 走标准 MCP 协议，不绑定某个 CLI 的私有机制 |
| G5 | 不为钉钉接入自建一套长连接服务 | 复用已有的官方开源能力，减少维护面 |

## 3. 非目标

- 不做多用户协同。这是**个人工具**，只服务持有这台电脑和这个钉钉账号的人。
- 不做 Web 管理界面、不做消息历史查询、不做数据统计。
- 不做把整个 CLI 会话镜像到手机（那是阶段 4 的远程控制，不在本期范围）。
- 不承诺 agent 在没有回复时能自动做出决策。桥只负责送达和回传，决策权在人。

## 4. 使用者与场景

**使用者**：本机开发者本人。既是钉钉组织的管理员（能给自己开权限），也是唯一回复人。

### 场景 S1：离开电脑，任务卡住（P0，主场景）
agent 在跑测试重构，需要确认「旧配置文件是删掉还是保留备份」。人已经在地铁上。手机钉钉收到一条带项目名的消息，直接回「保留备份」。agent 收到答案继续跑。

### 场景 S2：并行多项目，两边都在问（P0）
A 项目和 B 项目的 CLI 同时开着。两边都可能推问题到同一个手机会话。人必须能分辨哪条消息在问哪件事，回复不能串。

### 场景 S3：人在电脑前，不想被打扰（P0）
敲 `dtmcp off`，此后 agent 提问走原生本地交互，不发任何钉钉消息。期间任何 agent、任何项目都不推送。

### 场景 S4：手机上先看到问题，但回到电脑前处理（P1）
在手机上看到问题，决定回工位再答。回到电脑，在另一个终端窗口敲 `dtmcp reply Q3 保留备份`，手机端那条问题随即标记为已回答，不再重复提醒。

### 场景 S5：人迟迟没回复（P0）
agent 不应该无限期挂死。超时后拿到一个「未回答」状态，可以自行决定继续干别的活、稍后再查、或改用本地提问。

## 5. 功能需求

### FR1 远程提问（P0）
agent 通过一个 MCP 工具发起提问，参数至少包含：问题文本、可选的候选项列表、可选的超时秒数。

**验收**：
- 开关打开时，手机在 X 秒内（X ≤ 15）收到一条消息，内容包含问题文本、候选项、项目标识、问题编号。
- 人回复后，工具以「已回答」返回，返回值里能取到原始回复文本。
- 开关关闭时，工具**不发送任何钉钉消息**，立即返回「已禁用」，agent 据此改用本地提问。

### FR2 全局开关，双向可切（P0）
- 一个全局开关，作用域覆盖所有 agent、所有项目、所有正在运行的会话。
- 生效时机是「提问那一刻」，不是「会话启动那一刻」——中途切换立即影响后续提问，无需重启 agent。
- 三个入口：本机 CLI 命令（`dtmcp on` / `dtmcp off`）、手机钉钉指令、状态查询命令（`dtmcp status`）。
- 手机指令须用保留前缀（如 `#开` / `#关`），避免和答案文本歧义。

**验收**：
- 在 A 项目执行关闭，B 项目的下一次提问不推送。
- 在手机发 `#关`，本机 `dtmcp status` 显示已关闭，且后续提问不推送。
- 开关状态持久化，进程重启后保持。

### FR3 两端回复，先到先得（P0）
同一个问题，手机端回复和电脑端回复（`dtmcp reply`）都能生效；先到的那个决定答案，后到的被拒绝并给出提示。

**验收**：
- 电脑端先答，手机端随后回复同一编号时，收到一条「该问题已由电脑端回答」提示，原答案不被覆盖。
- 手机端先答，`dtmcp reply` 返回明确的「已回答，答案为 X」，不静默丢弃。

### FR4 并发多问题不串（P0）
多个问题可同时处于待答状态，不强制串行排队。人的回复必须能被可靠归属到正确的问题；无法判定时**必须追问而不是猜**。

**归属规则（按优先级）**：
1. 保留指令前缀（`#开` / `#关` / `#忽略`）→ 当指令处理，不当答案
2. 消息含 `#Q<id>:` → 定向该问题
3. 仅存在一个待答问题 → 归属该问题
4. 多个待答问题且无编号 → 回复追问「请带编号」

**验收**：S2 场景下两个项目同时提问，用编号回复时归属正确；不带编号时收到追问而非把答案给错问题。

### FR5 超时返回待答，可回查（P0）
提问工具内部等待一个有限时长，超时后返回「待答」状态和问题编号，agent 稍后可用另一个工具回查结果。问题在超时后依然存活，人回复仍然会被记录，并在 agent 回查时拿到。

**验收**：
- 超时不报错误、不抛异常，返回可区分的状态。
- 超时期间人回复，随后 agent 回查能取到答案。
- 超时时长可配，默认值必须小于常见 MCP 客户端的工具调用超时，避免答案被客户端切断。

### FR6 问题作废（P1）
agent 或人可以取消一个不再需要的待答问题；作废后该问题的后续回复不再归属，手机端相应提示。

### FR7 状态可自检（P0）
一个查询接口，返回：开关状态、目标会话是否解析成功、消息监听是否正常、当前待答问题列表、底层依赖是否已登录。

**验收**：出问题时，这个接口的输出足以区分「开关关着」「没登录」「监听断了」「已推送但没人回」四种情况。

### FR8 跨 agent 兼容（P0）
提问能力以标准 MCP server 形式提供，不依赖任何单一 agent CLI 的私有扩展（hook、自定义 channel、SDK 私有回调）。至少在 Qoder 和 Kimi 两个客户端下，配置方式只有 `command` + `args` + `env` 的差异。

### FR9 失败不静默（P0）
底层依赖不可用（未登录、组织未开权限、会话无法解析、发送失败、监听断开）时，提问接口必须返回**可区分的 blocked 状态和原因**，绝不出现「agent 以为推了但实际没推」。

**验收**：拔掉登录态后提问，工具在数秒内返回 blocked 且原因明确；agent 能据此回退本地提问而不是干等。

## 6. 阶段路线

需求按阶段交付，每阶段有明确退出标准。**架构必须让前一阶段不成为后一阶段的障碍**——这是本项目最主要的架构约束来源。

| 阶段 | 内容 | 退出标准 |
|---|---|---|
| **1** | agent 主动提问 → 手机答 → 继续 | FR1–FR9 全部通过；在 Qoder 下完成一次真实的「地铁上回答」 |
| **2** | 工具的授权审批（危险操作如 `git push`、删除）推到手机确认 | 人在手机上完成一次 approve，电脑端 agent 拿到结果继续执行 |
| **3** | 任务完成 / 报错 / 长空闲等事件通知（单向，不阻塞） | 一次完整任务结束后手机收到摘要，无需回复 |
| **4** | 手机与电脑双向，手机可直接下达指令 | 人在手机上发起一个新任务，agent 在电脑端执行 |

阶段 2/3 依赖 agent 侧的 hook 或权限回调机制，属于「客户端相关」；阶段 1 属于「协议通用」。**这个差异必须在架构上隔离开**，否则阶段 2 会把阶段 1 的通用性污染掉。

## 7. 非功能需求

| 编号 | 要求 |
|---|---|
| NFR1 | **零外部基础设施**：允许一个本机常驻进程，但不需要公网地址、域名、数据库、容器 |
| NFR2 | **尽量少配置**：不要求用户去开放平台建应用、配权限、配卡片模板 |
| NFR3 | 消息监听进程异常退出后自动重连，退避有上限，不影响已在待答的问题 |
| NFR4 | daemon 重启后能从持久化状态恢复待答问题，人此前已收到推送，重启后仍能答上 |
| NFR5 | 同一时刻只允许一个 daemon 实例持有钉钉消息流；重复启动必须失败或复用，不能产生两个竞争消费者 |
| NFR6 | 凭证与 token 不落盘、不进日志、不进消息内容 |
| NFR7 | **推送到手机的内容默认最小化**：只推问题文本和项目标识，不推完整命令、文件路径正文、代码片段、环境变量。需要附带上下文时必须显式开启 |
| NFR8 | 状态文件与本地 socket 权限受限（用户可读写，其他用户不可） |
| NFR9 | 从提问发出到手机收到消息的可感知延迟 ≤ 15 秒 |
| NFR10 | 关闭状态下的提问路径开销 ≤ 50 毫秒（不产生网络调用，不做进程启动） |

## 8. 约束与依赖

| 项 | 内容 | 风险 |
|---|---|---|
| D1 | 依赖钉钉官方开源的 `dws`（DingTalk Workspace CLI）提供消息收发与事件监听 | 上游能力边界变化会影响本项目；已核实所需命令存在，见设计文档选型章节 |
| D2 | `dws` 采用个人 OAuth 登录，组织需开启「CLI 访问管理」 | 用户本人是管理员，可自助审批；首次需浏览器交互登录，必须由用户手动完成 |
| D3 | 运行环境 macOS + Node.js（本机 v26） | 无 |
| D4 | 钉钉消息以**用户本人身份**发出，不是机器人身份 | 手机收到的消息看起来是「自己给自己发的」，需要在消息正文里明确标注来源，避免误认 |
| D5 | 待核实：`dws` 能否向本人发起单聊 | 若不行，需退化成一个专用小群，影响监听目标与 FR1 的消息形态 |
| D6 | 待核实：同一账号多个 `dws` 订阅进程是否互相抢事件 | 若抢，FR5/NFR5 的「单 daemon 独占」从建议变为强制 |
| D7 | `dws` 的卡片发送目前只支持流式文本，不接受按钮组件 | 阶段 1 用纯文本 + 编号回复即可；阶段 2 的「按钮审批」需另行评估 |

## 9. 成功度量

- **主指标**：一次「人不在电脑前」的真实场景中，agent 提问到继续执行的往返耗时。目标：人在手机上看到消息后，10 秒内 agent 已拿到答案继续干活。
- **可靠性**：连续 20 次提问，零「静默丢失」（即不存在「agent 以为推了但手机没收到」）。
- **采纳**：用户在一周内实际使用次数 ≥ 5，说明比回到电脑前敲键盘更省事。若低于此，重新评估这个需求是否真实存在。

## 10. 决策记录（摘要）

| 决策 | 结论 | 依据 |
|---|---|---|
| 是否自建钉钉长连接 | 否，复用 `dws` | 省掉建应用、配权限、维护 SDK；FR1–FR9 不需要机器人身份 |
| 多会话如何区分 | 编号前缀 + 唯一待答时自动归属 + 无法判定则追问 | 见 FR4；编号是手机端唯一可靠的上下文线索 |
| 并发是否排队 | 不排队 | 多项目并行时排队等于人为加锁，用得越久越烦 |
| 超时行为 | 有限等待 + 返回待答 + 允许回查 | 无限等待会被 MCP 客户端的工具超时掐断，且人可能几小时后才看到 |
| 开关粒度 | 全局，提问时刻读状态 | 状态文件让任意项目里的一条命令影响所有会话 |
| 卡片按钮 | 阶段 1 不做 | 受 D7 限制，且文本 + 编号已满足 FR1/FR4 |
| 传输方式 | stdio MCP + 本机 Unix socket daemon | FR8 要求跨 agent，stdio 是目前最普遍的支持方式；NFR1 要求不出公网 |

详细权衡见设计文档。
